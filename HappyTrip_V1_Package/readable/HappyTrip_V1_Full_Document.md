# HappyTrip Skill V1 产品需求文档

版本：1.0.0　｜　日期：2026-09-29　｜　形态：旅行照片创意 Skill

## 1. 目标与交付边界

HappyTrip 把旅行照片变得更好看、更好玩、更值得收藏。用户通过上传素材和一句自然语言，完成照片修整、局部创意、纪念作品或旅行故事，不必自行编写长提示词。

本次交付是可以交给开发 Agent 的需求、设计、模式卡、提示词和 Skill 主文件。它不是已经接通模型的在线修图产品，也不包含已完成的十八种实图效果验证。`happytrip/` 是文本型 Skill 包，运行时仍需宿主提供看图、生图、编辑和必要的合成能力。

文章的十二种玩法保留原编号与名称，新增六种沿用 B 编号；不把所有候选或动态玩法加入首版。原文的三组组织为“基础玩法”“创意出片”“网感大片”[S1，第 1、7、15 页]。Fix / Play / Collect / Story 是双方讨论后采用的使用入口，不冒充原文章节。

### 1.1 已确认与本次设计补充

| 层级 | 内容 |
|---|---|
| 已确认范围 | 原文 A01–A12，以及 B01、B03、B04、B14、B16、B22，共十八种静态玩法。 |
| 已确认方向 | 四条入口、单图与多图、最少追问、可选标题配文、先打磨八种 P0。 |
| 本文具体化 | 数据字段、能力协商、合成策略、质量门槛、错误状态、开发任务与测试条件。 |
| 不从原文推导 | API 型号、价格、服务可用性、热度排名、跨平台安装路径和实测成功率。 |

A 类玩法属于原文改编，B 类玩法来自前序已确认的扩展设计。所有模板均为产品化整理，不是原提示词逐字重印。原文章节、约束与页码见来源说明；补充的工程默认值均按设计要求理解。

### 1.2 非目标

V1 不开发实时相机、视频或 GIF 模式，不自动发布社交平台，不做完整地图导航，不默认添加账号、积分、订阅、支付与云相册，也不重新研究社交热度排行榜。轻量调试工作台可以后续附加，但不得让前端建设阻塞文本 Skill 的使用。

## 2. 用户需求与四条入口

| 用户想法 | 入口 | 典型结果 |
|---|---|---|
| 这张照片不错，但背景乱或曝光不好 | Fix / 修好它 | 去除指定游客，自然调光，自然美颜。 |
| 不要大改，加一点有趣效果 | Play / 玩一下 | 原位贴纸、美食飞溅、文字构物、手写注释。 |
| 把这段旅行做成一件纪念作品 | Collect / 变成纪念品 | 明信片、行李箱贴纸、冰箱贴对照、纸雕、玻璃球、路线照片地图。 |
| 想让我成为这段旅程的主角 | Story / 讲一个旅行故事 | 拍立得公仔、人物海报、双重曝光、旅行漫画。 |

A09 演唱会氛围属于 Play 入口，但执行边界为整图重构。界面分类不能代替编辑权限判断。

## 4. 端到端流程

接收用户意图与素材，核对素材是否实际可用，再判断意图与模式。已指定模式则不重复展示完整菜单；没有指定时，推荐二至三个与素材匹配的模式，并解释一句适用原因。不能仅因用户上传了照片就擅自开始三套付费生成。

用户选择模式或授权“你决定”后，收集影响正确性的最少信息，生成编辑计划，检查能力与预算。信息充分的常规任务直接执行；只有身份目标、事实顺序、额外付费或范围冲突等关键缺口才追问。生图、合成、验收之后交付结果；未通过验收的候选不冒充最终成图。

### 4.1 必须追问的情况

多人图无法判断保留谁；A06 不止一个候选主体；A11 没有目标词或目标绑定；B22 不知道地点顺序却要求路线；用户同时要求“构图完全不变”和重新摆姿态；严格保真但宿主缺少必要合成能力；生成计划超过用户预算。这些是真实信息缺口，不是重复索要已给出的授权。

### 4.2 可以省略的情况

不需要题字的玩法可省地点、日期和标题；未提供日期就不显示日期，不把系统当前日期当拍摄日。中文对话默认中文文案，双语仅在用户选择时开启。一般创作描述可以生成，但不创造用户的私人经历、同行关系或精确行程。

## 5. 输入需求

### 5.1 公共字段

| 字段 | 规则 |
|---|---|
| mode | `auto` 或一个已收录 ID；同时识别中文别名。 |
| photos | 已解析为可读取资产的素材列表；标记 base、person、scene、pet、style、container 等角色。 |
| user_goal | 用户原始目标；用于处理模式与保护要求之间的冲突。 |
| targets | 明确编辑对象，可用描述、框选、遮罩及对应照片 ID。 |
| protected | 要保留的人、物、文字、区域及是否要求严格底图保护。 |
| facts | 用户确认的地点、日期、故事事实，逐项记录来源。 |
| visual_style | 真实、复古、水彩、手账、轻涂鸦、Q版、电影感等模式内选项。 |
| output | 比例、语言、标题、配文开关；默认不强制给保真修图裁成竖版。 |
| mode_options | 行李箱素材清单、物体文字绑定、漫画格数、路线顺序等专用字段。 |
| budget | 最大图像调用次数、允许修复次数；货币上限仅在有可靠报价时使用。 |

素材数量是工作流边界，不表示后端 API 的最大图片数。后端不支持一次接收全部素材时，应分批处理或让用户选择，不能静默丢弃。

### 5.2 保留前版字段的兼容关系

前版 `preserve_identity=true` 映射为可见身份特征保护；不是精确生物识别保证。`preserve_background=true` 映射为背景内容保护，在 A09 等重构模式中发生冲突时需要解释或调整模式。`extra_notes` 继续存在，但不再同时承载主体名、食物名、路线与文字绑定，以免参数含义漂移。

前版“原图质量差先轻修整”改为“识别问题并建议可选修整”。这是一项显式工程收紧：未经用户同意，不自动连做美颜、去游客、换天空等额外操作。

### 5.3 输出预设

Fix、A06、A10、A11、A12 默认保留原比例；A05 默认横版 3:2；A07 与 B03 默认 4:3；B04 默认 1:1；其余创作默认 3:4。用户指定比例优先，但不得因此强行裁掉受保护的人物或地标。若后端无该原生比例，使用等比布局或明确裁剪方案，不宣称任意尺寸都能原生生成。

## 6. 功能需求与可验证条件

| ID | 功能 | 验收条件 |
|---|---|---|
| FR01 | 素材核对 | 只有链接名、过期 ID 或未上传照片时，不调用编辑工具，明确缺少哪张素材。 |
| FR02 | 模式选择 | 识别十八个 ID 与常用别名；直接指定不再推荐其他模式。 |
| FR03 | 自动推荐 | 输入相同结构化特征时，规则结果可复现；没有素材不会臆断照片内容。 |
| FR04 | 权限边界 | 所有任务输出一份编辑计划，说明允许改变与必须保留的内容。 |
| FR05 | 事实保护 | 未提供日期不生成日期，未知路线顺序不画有方向的行程线。 |
| FR06 | 分层制作 | B01 严格使用原片合成；A12 支持底图与注释层分离；B22 准确文字与照片确定性排版。 |
| FR07 | 多图覆盖 | A07、B16、B22 保存来源映射；每张选用素材可追溯，未用素材有明确说明。 |
| FR08 | 局部返工 | 单格漫画或单枚贴纸失败时，只修复失败单元，保留已经通过的单元。 |
| FR09 | 透明状态 | 区分最终成图、候选、提示词方案、能力缺失、失败；不生成假下载地址。 |
| FR10 | 可选配文 | 标题和配文单独保存；宿主禁止生成图后附文时，遵守宿主交付规则。 |
| FR11 | 文件与隐私 | 不覆盖原图、不自动发布、不把密钥或精确定位写进公开成图。 |
| FR12 | 能力降级 | 没有编辑能力时只提供清晰标记的提示词方案，不宣称完成修图。 |

## 7. 质量原则

“尽量保留原图”“原图没有生成式重绘”和“像素完全不变”是三种不同的承诺。第一种是生成目标；第二种需要明确复用原始素材；第三种还要求一致的画布、颜色处理、无损导出与未编辑区域比对。仅凭提示词不得给出第三种承诺。

A01、A03、A06、A10、A11 以限定编辑区域为主；A02 允许全图色彩变化但不改变内容与几何；A12 是叠加图层；A05、A07、B01、B22 是生成素材与排版组合；A04、A08、A09、B03、B04、B14、B16 允许艺术重构。严格程度不是一个可以覆盖全部模式的单一滑块。

生成式补全不能被描述成真实找回被遮挡区域。艺术海报、漫画分镜与演唱会重构应在制作记录里标记创作性质。这里要求的是诚实说明制作方式，不要求所有成图都印上大块说明文字。

## 8. 输出与交付

必需输出为状态、所用模式、实际图像资产或清晰的能力缺口。生成工具支持文件交付时保存最终 PNG 或用户指定格式；每个文件必须能实际读取。

可选输出为标题、社交配文、编辑摘要、原图与结果对照、透明装饰层及项目清单。配文不是强制营销话术，不统一使用“AI 改变旅行”等句式。前版“每次成图后都附文”改为宿主允许时提供，避免与原生图片工具的响应约束冲突。

项目记录建议包含：`request.json`、`plan.json`、`result.json`、`validation.json` 和实际输出文件。普通用户默认只看到成图与必要说明；给开发者的调试记录不得暴露底层密钥或临时下载凭证。

## 9. 可选轻量工作台

若需要可视化调试，可实现一页式工作台：素材区、四类模式选择、当前模式参数、生成状态和前后对照。高级项折叠；点击修改目标时以图片标注代替长文字；移动端单列，底部保留主要操作。

信息架构为：开始页 → 素材与模式 → 编辑计划／必要确认 → 生成与修复 → 结果。无需先开发用户中心、图库市场或计费系统。照片拖入后以本地预览显示，只有用户确认生成时才按所选宿主或服务的实际机制发送素材。

## 10. 发布门槛与不确定项

静态包发布门槛：十八种模式齐全，编号稳定，模板变量有定义，文件链接有效，来源与扩展内容明确，示例可解析。

可执行 V1 发布门槛：P0 与 P1 均通过实图验收；所有严格保真承诺有技术路径和检查证据；无图、错图、预算、失败与隐私场景可正确处理。没有测试的模式应标注“待验证”，不能写“效果已稳定”。

接入时仍需确认宿主的工具能力、允许的图片格式和大小、真实调用参数、费用与存储策略。这些属于部署事实，不从文章或本份设计推定。


# HappyTrip Skill V1 开发方案

本文定义产品内部协议与推荐实现边界，不是任何模型提供方的 API 文档。接口名是拟议的应用内部命名；不能直接当作当前宿主的可调用工具。

## 1. 架构：先 Skill，后可选执行器

最小使用形态是 `SKILL.md + 模式卡 + 路由与质量规则`。Agent 读取用户图片，选用模式卡，调用所在宿主实际提供的工具。单纯把十八段提示词一次塞进系统提示词，不足以解决素材绑定、真实信息与保真合成问题。

工程化形态在同一模式配置之上增加能力适配器、素材注册表、计划器、合成器与验收器。V1 不要求自建支付或账户系统。

```text
用户意图 + 已解析素材
          |
素材核对 / 目标绑定 / 事实表
          |
模式路由 + 编辑计划 + 预算检查
          |
能力适配器 ---- 缺能力 ----> 提示词方案 / 请求补充
          |
图像生成或局部编辑
          |
确定性合成：原片 / 遮罩 / 文字 / 照片卡
          |
质量检查 ---- 单元失败 ----> 有预算的局部修复
          |
真实结果文件 + 制作记录
```

以上为逻辑架构，并非已部署服务。纯文字 Skill 不会凭空获得合成器或本机图像处理权限。

## 2. 模块职责

| 模块 | 输入 | 输出与职责 |
|---|---|---|
| Asset Registry | 宿主真实文件或附件引用 | 可读取资产、角色、尺寸、方向、内部哈希；拒绝无效引用。 |
| Intent Router | 用户目标、照片特征、模式配置 | 模式选择或至多三个建议，不生成照片事实。 |
| Fact Ledger | 用户文本、确认信息、可选已核实来源 | 带来源和确认状态的地点、日期、顺序、故事记录。 |
| Planner | 模式、素材、保护项、能力、预算 | 有依赖关系的步骤、编辑范围和缺口。 |
| Prompt Compiler | 模板与规范化参数 | 无未解析变量的文字指令，分离素材内容与控制指令。 |
| Image Adapter | 内部图像请求 | 映射到真实工具参数，返回候选与实际状态。 |
| Compositor | 原片、生成资产、遮罩、版式、准确文字 | 合成后的无损图像、变换记录与来源映射。 |
| Validator | 编辑计划、素材与候选 | pass / warn / fail / not_run，给出检查理由。 |
| Exporter | 已验证的文件与记录 | 实际可读取的交付物，不构造不存在的链接。 |

## 3. 能力协商

能力不是根据模型商品名猜测，而是由宿主描述、实际工具契约或接入测试确认。能力值使用 `true / false / unknown`，未知不能按支持处理。

```json
{
  "vision": "unknown",
  "image_generation": "unknown",
  "image_editing": "unknown",
  "masked_editing": "unknown",
  "multiple_references": "unknown",
  "transparent_assets": "unknown",
  "local_composition": "unknown",
  "exact_text_rendering": "unknown",
  "geographic_rendering": "unknown",
  "max_reference_images": null
}
```

原文的模型名按来源记录，不硬编码为 API 型号。适配器的模型标识、调用方式与限制从配置注入，并在实际接入时核对官方工具说明。宿主原生生图工具使用自身契约，不能因为本模板有一个 `prompt` 字段就假定所有工具都接受它。

### 3.1 降级策略

没有看图能力时，不能“自动识别照片主体”，只能使用用户文字和明确的素材角色；无法判定目标就追问。没有生图能力时只交付 `prompt_only` 方案。没有遮罩但有合成器时，可生成目标资产后限定区域合成；两者都没有时，严格局部保真任务进入 `needs_capability`。

B01 严格原片对照海报缺少合成器时不降级为整张海报生成后声称原片不变。B22 无地理渲染能力时使用明确标注的概念行程图；但仍需要已确认顺序才能连接节点。

## 4. 数据协议

建议用 UTF-8 JSON 存放配置和任务，避免与实际模型服务的参数同名混用。以下字段是内部数据结构，不是供应商请求样例。

### 4.1 资产

`photo_id` 是内部稳定 ID；`ref` 是宿主真实已解析引用，示例 ID 不能直接调用工具。`roles` 可同时含 base 与 scene。坐标统一基于方向已归一化的画布；框选 `[x,y,w,h]` 采用 0–1 归一化范围。遮罩必须与对应图像尺寸及方向一致。

```json
{
  "photo_id": "p01",
  "ref": "resolved_by_host",
  "roles": ["base", "person", "scene"],
  "width": 2400,
  "height": 3200,
  "orientation_normalized": true,
  "input_sha256": "record_at_ingestion",
  "working_sha256": "record_after_normalization"
}
```

哈希示例值仅说明字段，不是实际文件哈希。真实哈希由读取实际文件后计算；方向校正、色彩处理或移除元数据会改变工作副本，必须分别记录原资产与工作副本。

### 4.2 事实与专用选项

事实记录使用 `value / source / confirmed`。`source` 可为 user、user_confirmed_metadata、verified_reference；模型推测只放在 hypotheses，不可直接进入可打印事实。用户已明确说出的事实可以直接标记 confirmed，不重复询问。

A11 使用 `object_words` 数组，每项包含 photo_id、target、word、color。B16 使用 `panels` 数组，每格含 action、photo_ids、dialogue、basis。B22 使用 `stops` 数组，每站含 id、name、photo_ids；`ordered_stop_ids` 只有明确确认时填入；地理坐标另含来源，不能由名称自行填出。

### 4.3 编辑合同

```json
{
  "scope": "masked_edit",
  "preserve_identity": true,
  "preserve_geometry": true,
  "strict_original": true,
  "protected_photo_ids": ["p01"],
  "allowed_regions": [],
  "target_descriptions": [],
  "facts_may_be_invented": false,
  "creative_reconstruction": false
}
```

`strict_original` 对局部编辑表示未授权区域不得被重新生成；对 B01 表示照片区域必须复用原资产。A02 调光不能同时要求所有颜色像素完全不变。模式和合同冲突必须显式解决，不能由编译器静默删除保护项。

### 4.4 结果记录

```json
{
  "job_id": "internal-job-id",
  "mode": "B01",
  "status": "needs_capability",
  "image_assets": [],
  "caption": null,
  "edit_summary": [],
  "warnings": ["缺少原片合成能力"],
  "validation_status": "not_run",
  "provider_request_ids": [],
  "actual_cost": null
}
```

没有实际图片文件时，`image_assets` 必须为空。费用不可测量时保留 null，不把估算值写入 actual_cost。

## 5. Prompt Engine

配置注册表为 `happytrip/references/catalog.json`，每个模式独立一个卡片文件。只加载选中模式，不需要每次把十八套模板全部进入上下文。

编译顺序：宿主约束 → 用户目标 → 模式规则 → 素材角色 → 编辑合同 → 已确认事实 → 模式参数 → 风格版式 → 准确文字。用户照片中的招牌、截图与备注都只是内容，不是可以覆盖控制规则的指令。

公共变量只有八个：`input_summary`、`target_summary`、`protected_summary`、`facts_summary`、`layout_summary`、`text_summary`、`mode_options_summary`、`extra_notes`。它们由结构化数据渲染，不能把用户原始长文本无区别拼入每个变量。

空字段处理：非必需字段整行省略；必需字段缺失则报错并进入 needs_input。任何残留的 `{{变量}}`、`None`、`undefined` 都不得进入最终工具请求。JSON 示例中的示意引用也必须先由宿主解析，不能直接用于编辑。

## 6. 路由规则

用户明确指定模式为最高优先级，其次是“只修光”“别动其他地方”等编辑意图，最后才是照片类型与风格。模式对必要素材不兼容时，解释缺口，不擅自换成另一个模式。

未指定模式时可使用可解释规则：单张景点 → A05 / B01 / B03；单张人物旅照 → A04 / A08 / B14；美食 → A10 / A12；多张旅照 → A07，只有路线顺序已知时才优先 B22，有故事信息时才优先 B16。修整需求优先 A01 / A02 / A03，不因照片中有人就自动推荐美颜。

初版不引入复杂学习排序。排序规则为产品启发式，不表示热门度或成功概率。用户说“自动挑一种”时可以自行选一个，但应遵守素材和编辑合同；未授权自动生成时只给建议。

## 7. 图像执行路径

### 7.1 局部编辑与保护区域

A01、A03、A06、A10、A11 的理想流程是：固定原画布 → 确定目标与保护区域 → 获得编辑候选 → 合成 → 检查非编辑区域。不能只发送“其他完全不变”就认定保护成功。

设原片为 I0、同画布候选为 Ig、有效编辑遮罩为 M，合成定义为：

```text
Iout = (1 - M) * I0 + M * Ig
```

有效编辑遮罩必须包含白边、投影、飞溅与羽化带等所有允许改变区域。对 M=0 的区域，可在统一色彩空间、尺寸和方向的解码像素上逐像素比对。该检查只证明未授权区域复用正确，不证明编辑区域的隐藏内容符合真实世界。

像素保护以无损主文件验收。JPEG 重编码、缩放与颜色配置转换都可能改变像素，因此不要拿不同处理链的两张导出图直接宣称全图无变化。

### 7.2 叠加与准确文字

A12 在原片上增加独立涂鸦与文字层；A05、A08、B01、B04、B14、B16、B22 的准确标题、日期与地名优先后期排版。模型可以生成风格与空白区域，但不承担必须零错字的信息层。

优先读取已有结构化文字和直接视觉检查，不默认运行 OCR。检测到文字错误时重排文字层，避免重做整个图像。字体与素材授权需按实际选用资源处理；本包不附送系统字体文件。

### 7.3 B01 原片保留

分为生成冰箱贴资产、构建色彩背景、置入原片、排版文字四步。原片区域必须来自注册资产。默认 `contain` 完整显示，记录缩放与边距；不使用生成式扩图填满原片区域。若用户要求原尺寸像素保持，采用足够大的画布容纳原图，不缩放原片。

生成器只收到制作冰箱贴的任务；如果一次生成完整海报，无法凭画面相似度证明照片未重绘。此路径不得用于兑现严格保真承诺。

### 7.4 A07 多图贴纸

先建立素材清单和优先级，再生成统一风格贴纸及空箱体，最后将贴纸贴合进上下内衬。每张贴纸保存 source_photo_ids。所有选中素材必须有结果或明确未采用原因，不以“模型自动挑选”为理由静默漏图。

单次参考图能力不足时，按实际能力分批或逐项生成。拼接联系表是可选输入方法，但会缩小细节；采用前应评估是否还可识别原素材，不能把联系表当无限张高分辨率参考的替代品。

### 7.5 B16 漫画

先形成三格或四格结构化分镜，锁定角色与照片对应关系，然后选择单页生成或逐格生成。逐格模式复用相同人物参考和视觉约束，最终统一边框与文字。用户提供经历时忠实改编；没有经历时只使用已明确为想象的剧情。

### 7.6 B22 地图

默认使用已确认顺序的示意路线，不画仿真地理底图。无顺序则不连线，或先询问。真实地理版仅在坐标来源、渲染能力与相应数据使用要求都已确认时启用。只有城市坐标时，站点连线不是道路导航轨迹，不输出实际行驶里程。

## 8. 任务状态、预算与错误

任务主状态为 `needs_input → ready → running → validating → succeeded`；也可进入 `needs_capability`、`prompt_only`、`failed`、`cancelled` 或 `completed_with_warning`。推荐模式不是已完成生成。候选已产生但检查失败，不能状态写 succeeded。

设计默认：每个任务图像调用上限为 4 次，单个阶段最多修复 1 次，修复也计入总上限。超过上限的 A07 多素材或 B16 逐格计划，在第一次额外调用前说明计划并征得授权，不能无界重试。此为产品预算默认值，不是模型计费事实。

有真实费用接口时记实际费用；否则只报告调用次数与估算依据。超时但后台状态未知时先查询原请求，不直接重复生成。服务拒绝或权限失败不自动切换到未经用户许可的新外部服务。

| 错误码 | 行为 |
|---|---|
| ASSET_MISSING | 点名缺失素材，等待补充，不猜测。 |
| TARGET_AMBIGUOUS | 请求确认编辑或保留对象。 |
| CONTRACT_CONFLICT | 解释保护项与模式冲突，先解决冲突。 |
| CAPABILITY_MISSING | 提供缺口或提示词方案，不声称成图。 |
| FACT_ORDER_UNKNOWN | B22 不画方向线，等待顺序或改地点集。 |
| BUDGET_EXCEEDED | 停止额外调用，列明已完成部分。 |
| GENERATION_FAILED | 记录实际错误，不生成假文件。 |
| VALIDATION_FAILED | 保留候选，修复失败单元或标记失败。 |

## 9. 隐私、数据与导出

原图只读，所有归一化、去元数据与修整写入工作副本。默认不解析精确定位；用户请求真实地理输出时再明确启用相关数据。导出的公开成图默认不带原片精确定位元数据，但不修改源文件。

本机执行器可以默认本地处理文件，但调用外部图像服务仍会发送所需素材。文本 Skill 不能保证宿主或服务商“绝不保存”或“永不训练”；应依据实际所用服务的政策说明，不把本地临时文件清理等同于第三方删除。

临时文件以任务为单位分隔，失败也可清理；正式产物仅保留用户选择的版本。密钥仅来自实际运行环境的安全配置，不进入前端、模板、日志或导出包。未得到用户指令，不向 X、Instagram、Facebook 自动发布。

## 10. 可选工程落地

执行器可用单一语言实现，推荐沿用开发者已有项目语言；不为此引入一套新 SaaS 脚手架。图像合成需要具备栅格、透明层与文字布局能力，具体库由接入环境确定并锁定版本。本方案不假定某个当前版本一定支持所需 API。

建议目录为 `src/assets`、`src/router`、`src/planner`、`src/adapters`、`src/compositor`、`src/validation`、`tests`；模块接口见实施计划。调试 UI 只调用统一任务服务，不直接持有模型密钥。

## HappyTrip

让旅行照片更好看、更好玩、更值得收藏。范围固定为十八种静态玩法。宿主的工具契约、图片处理规则与用户的明确限制优先于本 Skill。

1. 用户指定模式就直接使用；未指定则按目标与素材给二至三个建议。只有用户授权自动选择时，才自行选择一个开始执行。

每个建议只解释一句与素材的关系。没有素材只能按文字意图建议，不能声称“这张照片最适合”。不要把候选排名解释为社交热度或生图成功率。

## 4. 最少追问

照片里有多个主体时，先问要改谁；路线未知时先问顺序。次要题字可留空，风格使用当前模式默认值。用户已明确提供的地点与日期不重复确认。

常规单图已选模式且条件足够时直接执行，不再要求批准完整 PRD。需要更多调用、额外外部服务或与保护项冲突时，再针对该变化询问。

## 5. 示例交互

用户：“用 happytrip 把这张景点照片变成明信片。”

处理：核对照片可读 → A05 → 日期未给则省略 → 默认横版水彩 → 生图与排版 → 核对地标和文字。不要问年龄、行程预算、社交账户等无关信息。

用户：“这十张图做路线地图，顺序你看着办。”

处理：如果用户允许的是设计布局而没有真实行程顺序，不把上传顺序冒充行程；询问真实顺序，或提供明确不连线的地点集。若用户明确说“我只要虚构的视觉路线”，可以做艺术示意并记录其创作性质。


# HappyTrip 执行与质量规则

## 1. 分清五种边界

masked_edit 只改指定区域和必要过渡带；global_adjust 改光色但不改物体和几何；overlay 只加图层；hybrid_layout 生成资产后与真实素材排版；reimagine 允许艺术重构。类别 Fix / Play / Collect / Story 不自动决定编辑权限。

所有模式均不覆盖原文件。没有实际图像工具时只输出明确的提示词方案，不把一个生成计划称为成图。

## 2. 能力与工具契约

先确认实际宿主支持看图、参考图编辑、多图、遮罩、透明资产、文件读写、文字排版和合成中的哪些能力。未知按尚未确认处理。不要将注册表 input_max 当作服务商单次上限。

模板是语义指令，不是工具参数对象。调用时遵守真实宿主契约；特别是生成后是否允许附文、工具是否自动使用当前图片、附件需要真实引用还是本地路径，均由该宿主规则决定。

## 3. 保真与合成

局部修改需要保护同伴、脸、关键地标及用户指定区域。白边、投影、飞溅和羽化经过的区域要包含在允许修改范围内，不能把越界修改当作“很小所以无所谓”。

严格保护时，用原片重新合成非编辑区域。原图与生成结果必须同尺寸、同方向、同色彩处理后才能比较。无损主图的允许区域之外应保持基准像素；有缩放或 JPEG 重编码时不能宣传像素不变。

B01 必须复用原照片作为照片层；A12 优先独立涂鸦层；B22 照片卡、站点文字与路线采用确定性排版。能力不足时说明，不能以更强提示词代替缺失的合成能力。

## 4. 事实与艺术

原片可见内容与用户确认信息可进入作品；模型猜测留在候选说明。没有日期就不加日期，没有故事就不写真实经历，没有路线顺序就不画方向线。

艺术重构可以虚构视觉，但不得假称未经确认的旅程事实。A08 城市拼贴与 A09 重构属于创作；B16 用户提供的真实故事与允许创作的故事须分开记录。隐藏背景的补全是推断，不是事实恢复。

## 5. 文字和人物

准确标题、日期与地名优先独立排版。A11 的字形构物另验收词语准确和物体轮廓，不以普通字幕蒙混过关。不默认使用 OCR；已有文字数据和可直接看图的情况优先利用这些信息。

保留人物可见身份特征，不自动分析姓名或关系。美颜只对明确对象实施；不默认瘦脸、放大眼睛、改变年龄或给儿童加成人妆。几何保护与艺术重构冲突时先解决，不给不可能同时成立的承诺。

## 6. 失败与返工

默认最多四次图像调用，每阶段最多修复一次，修复计入总数。超预算先说明。局部、单贴纸、单格漫画和文字错误按最小单元返工；不能为了一个错别字重做整趟旅程。

生图失败、候选未过审、文件保存失败要区分。只有实际文件可读取时才提供下载引用。只拿到提示词则状态 prompt_only，没有实图验收则 validation_status=not_run。

## 7. 交付约束

用户默认得到实际结果与必要说明，不得到一大段内部工具参数。社交配文可选；如宿主要求图片生成后结束回复，遵守该要求，配文另行保留或在允许的阶段提供。

不自动分享或发布，不保证外部服务的数据保留政策，不输出未经核实的费用。任何“已安装”“已验证”“已生成”都应有对应证据，而不只因为文档中有这个功能名称。

# HappyTrip V1 验收与回归清单

验收分四层：文档与配置、确定性程序、宿主行为、真实图像。第一层通过不代表其余三层通过；模拟适配器不计入真实生图测试。

## 1. 本次文档交付检查

随包提供 `checks/validate_package.py`，只检查文件存在、十八种模式、八个 P0、模式卡章节、变量、来源分类、相对链接和 JSON 示例。使用 Python 运行：

```bash
python checks/validate_package.py
```

实际执行结果写入 `checks/VALIDATION-REPORT.md`。此脚本不调用模型、不访问社交平台、不验证视觉质量或跨宿主安装行为。真实图像案例在本次交付中均为 not_run。

## 2. 共同硬门槛

任何模式都不能在没有可用图像时声称编辑完成。不得把文章 PDF、文件名、过期链接或用户所说的“上次那张”当作当前已解析的照片。人像模式需要真实参考；一张群像中不得自行猜测谁是用户或同行者。

最终结果不得出现错误人物、无来源的私人事实或伪造链接。事实文字需要准确；任何未验证的日期、地点顺序、公里数、坐标、活动名称不能伪装为真实信息。用户要求局部修改时，不能交付全图重绘而不说明。

严格原片保护以可核对的合成来源和无损主图检查为依据；艺术重构则以用户意图、人物可见特征、视觉一致性和制作说明为依据。两者不共用同一个“相似度分数”。

## 3. 每个模式的关键验收点

| 模式 | 必须成立 | 典型失败 |
|---|---|---|
| A01 | 保留主角和同伴；只删指定对象；背景连接自然 | 把朋友删了，建筑出现重复纹理。 |
| A02 | 内容与几何不变；曝光自然；不自动美容 | 换了天空或五官，把全图锐化成 HDR。 |
| A03 | 指定人物、自然纹理、脸型保持 | 统一网红脸、过度磨皮、擅加妆容。 |
| A04 | 公仔、手持相纸、破框和场景延续同时成立 | 框内外重复主角，手指错误，只有普通边框。 |

## 5. 确定性合成测试

使用测试图片而非私人照片可以验证尺寸、透明层和遮罩。包括方向校正、边界框合法性、有效遮罩之外零差异、白边被纳入允许区域、文字不会越界、照片 contain 不裁主体、透明背景正确、错误素材 ID 被拒绝。

原片不重绘：检查 B01 的照片层来源 ID、工作副本哈希与最终变换记录。对于等比缩放后的成图，与同样缩放后的基准比较，不拿原尺寸图片的像素值直接比较。JPEG 不承担逐像素保真主文件职责。

## 6. 视觉测试方案

每种至少准备典型、边界、冲突三类素材，共五十四类案例设计。每例都需要独立记录结果；五十四是建议测试覆盖数量，不是已完成数量。人物、地标、食物、城市夜景、逆光、人群与不同宽高比应跨案例覆盖。

记录项：模式 ID、素材来源与授权、宿主与能力、执行日期、提示词版本、生成次数、候选文件、验收项、失败原因、修复、最终结论。视觉质量由人工复核；无法可靠自动检测的项目可以是 needs_review，不伪造自动验收通过。

## 7. 状态与发布标签

`not_run` 表示尚未运行；`pass` 表示指定检查已完成且通过；`warn` 表示不阻断但必须披露的问题；`fail` 表示不满足要求。一个通过结构检查的文本 Skill 包可以发布为“文档版”；只有真实模型与宿主验证完成后，才将对应能力标记为已验证。

V1 发布不使用未经测量的“成功率 99%”“像素级编辑保证”“全平台即装即用”等表述。失败回退和透明说明本身属于验收结果，不必为了展示成图而牺牲正确性。
